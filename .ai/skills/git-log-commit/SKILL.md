# Git Log Commit

작업한 코드의 물리적 변경 사항을 자동으로 요약하여 상세한 커밋 로그를 생성하는 스킬이다.

## 핵심 요구사항 반영

- **상세 요약**: 파일 변경 및 코드 수정을 물리적 관점에서 요약 (어떤 로직이 어떻게 바뀌었는지).
- **사용자 검토**: 생성된 메시지를 커밋 전 사용자가 수정할 수 있도록 제시.
- **활동 기록**: 커밋 완료 후 프로젝트 활동 로그(`.person/logs/activity.log`)에 기록.

## 인터뷰 기반 워크플로우

### Step 1: 변경 사항 분석 (Research)

- `git status`로 변경된 파일 목록 확인.
- `git diff`를 통해 실제 코드 변경 내역(staged/unstaged 모두 포함) 추출.
- 특히 `_core/utils/Resp.java`나 도메인 모델(`Board.java`, `User.java` 등)의 변화를 중점적으로 파악.

### Step 2: 커밋 메시지 초안 생성 (Drafting)

- **형식**: 자유롭지만 작업 내용이 불렛 포인트로 상세히 나열된 형태.
- **내용**: 
  - [파일/클래스명] : 변경된 주요 로직 또는 필드 요약.
  - (예: `BoardController.java` : 글 목록 조회 API 응답 처리 로직 수정)

### Step 3: 사용자 검토 및 수정 (Review)

- 생성된 초안을 사용자에게 보여주고 확인 요청.
- "이대로 커밋할까요? 아니면 수정할 부분이 있나요?" 질문.

### Step 4: 최종 커밋 및 로깅 (Execution & Logging)

- 사용자가 확정하면 `git add .` 및 `git commit -m "[최종 메시지]"` 실행.
- 실행 후 반드시 활동 로그 기록:
  ```bash
  echo '{"tool_name":"Skill","tool_input":{"skill":"git-log-commit","description":"커밋 메시지 자동 생성 및 커밋 수행"}}' | bash .ai/hooks/log-activity.sh
  ```

## 주의사항

- 변경 사항이 너무 많을 경우(예: 수천 줄), 핵심적인 파일 위주로 요약하고 "외 N개 파일 수정"으로 생략 처리한다.
- 커밋 전 반드시 사용자에게 메시지 수정 기회를 주어야 한다.
- 이미 커밋할 내용이 없는 경우(No changes) 적절한 안내 메시지를 출력한다.
